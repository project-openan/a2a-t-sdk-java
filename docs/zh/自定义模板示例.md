# 1 自定义模板示例

本文档通过一个端到端可运行的示例，演示如何用**自定义业务模板**（办公设备故障报修）+ `local_file` 资源加载模式，跑通 A2A-T 的 Task-T 全流程：客户端自然语言输入 → 槽位提取 → 模板渲染生成 prompt → 服务端校验并提取参数。

## 1.1 概述

### 1.1.1 本示例演示什么

示例业务：办公设备（打印机、电脑、显示器、投影仪等）故障报修。用户用一句话描述故障，客户端 SDK 按**显式指定的模板**抽取槽位并渲染生成 A2A-T 任务报文；服务端 SDK 对该报文做语义校验并按调用方 Schema 提取出结构化参数。

客户端选用 `generateTaskPromptFromText(String, TemplateUri)`：它要求显式传入 `TemplateUri`，因此**跳过场景识别**这条 LLM 调用，直接按指定模板做槽位提取与渲染，返回 `MetadataContent`，用 `promptText()` 取渲染后的报文。服务端选用 `validateTaskPromptAndDataFilling(String, Map, TemplateUri)`：校验任务报文合规性并按传入 Schema 提取参数，返回 `FilledParamData`，用 `data()` 取提取出的 `Map`。

### 1.1.2 适用版本与前置条件

| 项目 | 要求 |
| --- | --- |
| JDK | 17+ |
| 构建工具 | Maven 3.8+ |
| SDK | `net.openan.a2a-t.sdk:a2a-t-client` 与 `net.openan.a2a-t.sdk:a2a-t-server`，版本 `1.0.0` |
| LLM | 可访问的 OpenAI 兼容服务及 API Key |
| 资源模式 | `local_file`（业务内容从本地目录加载） |

> 本示例只演示 A2A-T SDK 本身，不引入 a2a-java、注册中心或 HTTP 链路。如需完整的 A2A HTTP+JSON/REST 串接，请参考《开发指南》与 `a2a-t-sample`。

## 1.2 本地资源目录

`local_file` 模式下，业务内容从本地根目录加载。根目录由 `A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR` 指定（见 [1.4](#14-env-配置)）。目录结构如下：

```
prompt-resources/
├── templates/
│   └── Task-T/
│       └── office-it/
│           └── printer-repair/
│               └── v1/
│                   └── zh-CN/
│                       └── template.md
├── slots/
│   └── Task-T/
│       └── office-it/
│           └── printer-repair/
│               └── v1/
│                   └── zh-CN/
│                       └── slot.json
└── scenarios/
    └── zh-CN/
        └── scenarios.json
```

要点：

- **`templates` / `slots` / `scenarios` 三类业务内容可本地化且本地优先、缺失回退内置**。`prompts`（LLM 提示词）与协商（Negotiation-T）资源恒从 classpath 加载——把它们放到本地目录不会被读取，SDK 只会忽略并输出 WARN 日志。
- `templates` 与 `slots` 的目录层级固定为 `{扩展名}/{业务域}/{业务名}/{版本}/{语言}`，即 `Task-T/office-it/printer-repair/v1/zh-CN/`。
- `scenarios` 没有 `Task-T` 段，直接是 `scenarios/{语言}/scenarios.json`；该文件**可省略**——本地根目录无此文件时装配期回退内置场景目录。
- 语言目录（本例为 `zh-CN`）必须与 `.env` 中的 `A2AT_LANGUAGE` 一致，否则对应的模板/槽位/场景资源找不到。
- 注意：虽然 `generateTaskPromptFromText` 本身跳过场景识别，但 `local_file` 模式下 `new A2ATClient(...)` 在**装配期**仍会调用 `loadScenarios` 做组件装配。`scenarios/{语言}/scenarios.json` 可以省略，本地缺该文件时回退内置场景目录、装配不会失败。本示例只覆盖自定义模板，可不放置场景目录（见 [1.3.3](#133-scenariosjson)）。

## 1.3 资源文件说明

### 1.3.1 template.md（模板）

模板定义任务报文的骨架，`{{槽位名}}` 是槽位占位符，渲染时会被替换为从用户输入提取出的实际值；占位符名必须与 `slot.json` 中的槽位名一一对应。模板分节、占位符标注 `（必填）/（选填）`、`要求：` 编号列表以及 `<尖括号>` 交叉引用的写法均对齐内置 Task-T 模板（如 `ran-energy-saving`）。

> `（必填）/（选填）`、`要求：` 等说明文字是渲染前的编写说明，渲染时会被剥离，不会出现在最终报文中（渲染结果见 [1.6](#16-运行与预期输出)）。它们与 `slot.json` 的 `description`/`x-a2at-value-constraint` 是槽位提取与语义校验的依据。

````markdown
## 操作类型(Operation Type)

{{操作类型}}（必填）

要求：

1. 请提供操作类型，取值范围：创建、修改

## 任务类型(Task Type)

办公设备故障报修

## 任务描述(Task Description)

{{任务描述}}（必填）

要求：

1. 请根据<操作类型>（创建/修改），动态提供任务描述信息：
   - 类型为【创建】时内容为：基于<任务对象>、<任务上下文>，发起办公设备故障报修请求，达成<任务目标>中定义的报修目标，并按照<预期输出>中定义的格式返回报修处理结果。
   - 类型为【修改】时内容为：基于<任务对象>、<任务上下文>，更新办公设备故障报修请求，达成<任务目标>中定义的报修目标。

## 任务对象(Task Object)

{{任务对象}}（必填）

要求：

1. 报修人：（必填）
   - 故障报修发起人的姓名
   - 举例：报修人："张伟"
2. 部门：（必填）
   - 报修人所属部门名称
   - 举例：部门："市场部"
3. 故障设备：（必填）
   - 发生故障的办公设备名称、品牌及所处位置
   - 举例：故障设备："三楼东侧会议室旁的惠普打印机"

## 任务目标(Task Target)

{{任务目标}}（选填）

要求：

1. 定义报修任务需达成的量化或定性目标，量化目标和定性目标不可同时选择，默认为定性目标。报修目标的具体说明如下：
   - 量化目标：期望完成维修的时间要求，目标值格式为具体时刻或时间区间；举例：期望完成时间：下午三点前
   - 定性目标：尽快受理并完成维修，恢复设备可用

## 任务上下文(Task Context)

{{任务上下文}}（选填）

要求：

1. 故障现象：设备发生故障的具体现象描述；举例：故障现象：开不了机，电源灯一直闪
2. 联系方式：报修人的联系电话；举例：联系方式：13800001234

## 预期输出(Expected Output)

{{预期输出}}（创建时选填，修改时无需填写）

要求：

1. 输出办公设备故障报修任务的报修结果，报修结果应包含以下信息：

### 报修结果基本信息

1. 报修受理状态
2. 报修任务唯一标识

### 报修结果详细信息

1. 故障设备信息
2. 维修处理要求
````

### 1.3.2 slot.json（槽位 Schema）

槽位 Schema 是一个 JSON Schema，声明每个槽位的类型、业务含义与取值约束。`properties` 下的键名即槽位名，必须与 `template.md` 的 `{{占位符}}` 对应；每个槽位下的 `description` / `examples` / `x-a2at-value-constraint` 三要素是 LLM 槽位提取的主要依据，写得越贴切提取越准。`required` 数组声明必填槽位（本示例对齐内置模板写法，保持为空，必填语义主要体现在值约束与描述中）。

### 1.3.3 scenarios.json（场景）

场景清单用于客户端装配期的场景目录加载。**本示例走 `generateTaskPromptFromText` 路径，不做场景识别**，因此不需要登记场景——`scenarios/{语言}/scenarios.json` 可直接省略，装配期会回退内置场景目录、装配不会失败。若需要本地场景识别，才需要放置该文件，其中 `scenario_code` 必须与模板目录路径一致：`Task-T/office-it/printer-repair/v1`。

```json
{
  "scenarios": [
    {
      "scenario_code": "Task-T/office-it/printer-repair/v1",
      "scenario_name": "办公设备故障报修",
      "description": "用于生成办公设备（打印机、电脑、显示器、投影仪等）故障报修/维修申请类的 A2A-T 任务请求，围绕报修人、部门、故障设备、故障现象、期望完成时间、联系方式等信息进行描述。",
      "example": "帮我创建一个办公设备故障报修任务，操作类型：创建；任务对象：报修人为张伟；任务目标：期望完成时间为下午三点前。"
    }
  ]
}
```

## 1.4 .env 配置

将以下内容保存为 `.env`（放置位置即进程工作目录，也可通过命令行参数指定完整路径）：

```properties
A2AT_LANGUAGE=zh-CN
A2AT_PROMPT_SOURCE_TYPE=local_file
A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR=./prompt-resources
A2AT_PROMPT_COMPLIANCE_ENABLED=false
A2AT_LLM_PROVIDER=openai
A2AT_LLM_MODEL=your-model-name
A2AT_LLM_BASE_URL=https://your-llm-gateway.example.com/v1
A2AT_LLM_API_KEY=your-api-key
A2AT_LLM_MAX_TOKENS=8000
A2AT_LLM_TIMEOUT_SECONDS=180
```

要点：

- `A2AT_PROMPT_SOURCE_TYPE=local_file`：启用本地文件资源加载。
- `A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR`：本地资源根目录。**相对路径以 `.env` 文件所在目录为基准解析**（不是进程工作目录）。上面的 `./prompt-resources` 表示资源目录与 `.env` 同级。
- 该目录在 `new A2ATClient(...)` / `new A2ATServer(...)` 装配期即被读取校验：**目录不存在会在构造期直接 fail-fast 抛异常，且不发起任何 LLM 调用**。
- `A2AT_PROMPT_COMPLIANCE_ENABLED=false`：本示例关闭生成阶段的前置合规校验，聚焦「生成 → 服务端校验提参」主线。
- `A2AT_LLM_MAX_TOKENS`：使用带推理（reasoning）的模型时需调大该值——推理会占用输出预算，过小会导致结构化为空。
- `A2AT_LLM_PROVIDER` / `A2AT_LLM_MODEL` / `A2AT_LLM_BASE_URL` / `A2AT_LLM_API_KEY` 按实际接入的 LLM 服务填写；此处均以占位符展示。

### 1.5.2 TaskTDemo.java

```java
package demo;

import java.nio.file.Path;
import java.util.Map;
import net.openan.a2at.sdk.client.A2ATClient;
import net.openan.a2at.sdk.core.model.MetadataContent;
import net.openan.a2at.sdk.core.model.TemplateUri;
import net.openan.a2at.sdk.server.A2ATServer;

public final class TaskTDemo {
    public static void main(String[] args) throws Exception {
        Path env = Path.of(args.length > 0 ? args[0] : ".env");
        String text = args.length > 1 ? args[1]
                : "帮我创建一个办公设备故障报修任务，操作类型：创建；任务描述：基于报修人、部门和故障设备信息，发起办公设备故障报修请求，达成任务目标中定义的报修目标，并按照预期输出中定义的格式返回报修处理结果；任务对象：报修人为张伟、部门为市场部、故障设备为三楼东侧会议室旁的惠普打印机；任务目标：期望完成时间为下午三点前；任务上下文：故障现象为开不了机、电源灯一直闪，联系方式为13800001234；预期输出：输出报修结果，包含报修受理状态、报修任务唯一标识、故障设备信息、维修处理要求。";
        TemplateUri uri = TemplateUri.of("Task-T", "office-it", "printer-repair");
        Map<String, Object> schema = Map.of(
                "type", "object", "properties", Map.of(
                        "报修人", slot("故障报修发起人的姓名"),
                        "部门", slot("报修人所属部门名称"),
                        "故障设备", slot("发生故障的办公设备名称、品牌及位置"),
                        "故障现象", slot("设备故障的具体现象"),
                        "期望完成时间", slot("期望完成维修的时间要求"),
                        "联系方式", slot("报修人的联系电话")));

        A2ATClient client = new A2ATClient(env);
        MetadataContent content = client.generateTaskPromptFromText(text, uri);
        System.out.println(content.promptText());
        A2ATServer server = new A2ATServer(env);
        System.out.println(server.validateTaskPromptAndDataFilling(content.promptText(), schema, uri).data());
    }

    private static Map<String, Object> slot(String description) {
        return Map.of("type", "string", "description", description);
    }
}
```

两个关键 API 说明：

- **客户端 `generateTaskPromptFromText(String, TemplateUri)`**：显式传入模板 URI，跳过场景识别，直接按该模板做一次 LLM 槽位提取并渲染，返回 `MetadataContent`（`promptText()` 即渲染后的报文）。相较 `generateTaskPrompt(Object)` 的场景识别路径，它省去识别那次 LLM 调用，且报文结果里带显式 `templateUri`。
- **服务端 `validateTaskPromptAndDataFilling(String, Map, TemplateUri)`**：校验任务报文合规性并按调用方 Schema 提取参数，返回 `FilledParamData`（`data()` 即提取结果 `Map`）。它需要显式 `TemplateUri`——本例 `TemplateUri.of("Task-T", "office-it", "printer-repair")` 逐段构造，与资源目录路径一一对应。
- 服务端 `schema` 是调用方提供的参数 JSON Schema（本例用 `Map.of` 内联声明 6 个业务字段），键名（`报修人`/`部门`/`故障设备` 等）与客户端模板槽位名（`操作类型`/`任务对象` 等）**刻意不同**：客户端负责把业务字段渲染进模板分节，服务端再从渲染后的报文里按自身键名重新提取，展示了 SDK 的跨键名适配能力。

## 1.6 运行与预期输出

在工程根目录执行：

```bash
mvn compile exec:java
```

> 首次运行需确保能联网解析 `net.openan.a2a-t.sdk` 依赖，并已正确填写 `A2AT_LLM_API_KEY` 等 LLM 配置。

预期输出分两段：先是客户端渲染出的 prompt 原文，紧随其后的是服务端提取出的 `data` Map（`FilledParamData.data()` 的字符串化结果）。

```text
## 操作类型(Operation Type)

创建

## 任务类型(Task Type)

办公设备故障报修

## 任务描述(Task Description)

基于报修人、部门和故障设备信息，发起办公设备故障报修请求，达成任务目标中定义的报修目标，并按照预期输出中定义的格式返回报修处理结果
```

## 1.7 常见问题

- **资源目录不存在，构造期即失败（零 LLM 调用）**：`A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR` 指向的目录不存在或路径非法时，`new A2ATClient(...)` / `new A2ATServer(...)` 在装配期 fail-fast 抛异常，且不会发起任何 LLM 调用。`local_file` 模式下业务内容本地优先、缺失回退内置，`scenarios/{语言}/scenarios.json` 可以省略（缺失时回退内置场景目录，见 [1.3.3](#133-scenariosjson)）。
- **输入超长 `input_text_too_long`**：FromText 生成与服务端校验入口均受 `A2AT_INPUT_TEXT_MAX_CHARS`（默认 16384）约束，超长的自由文本会在进入 LLM 之前直接以 `input_text_too_long` 快速失败，不消耗 LLM 调用。
- **`slot_validation_error`（`missing_required`）或 `validation_semantic_rejected`**：当 `slot.json` 的 `required` 声明了某槽位而输入未能提供时，客户端抛 `slot_validation_error`（`missing_required`）；而当报文的语义自相矛盾时，服务端以 `validation_semantic_rejected` 拒绝。二者都要求「模板 `要求：` 描述 ↔ `slot.json` 的 `description`/`x-a2at-value-constraint` ↔ 输入内容」口径一致。典型反例：任务描述写「尽快恢复设备可用」（定性目标）、任务目标却写「下午三点前」（量化目标）——量化/定性目标不可同时选择，会被服务端以 `semantic_mismatch` 拒绝。
- **Windows 控制台中文乱码**：Windows 控制台默认编码非 UTF-8 时展示中文会乱。可先执行 `set JAVA_TOOL_OPTIONS=-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -Dfile.encoding=UTF-8`（或 `chcp 65001`）再运行，使输出以 UTF-8 呈现。
